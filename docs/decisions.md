# 技术决策

[返回 README](../README.md) · 当前设计见 [architecture](architecture.md)

本页记录选择原因与代价。最初方案来自计划或早期阶段，不代表都实现过；当前方案以代码为准。每项固定使用六个字段。

## ADR-001 Java + Python 双服务

- **问题**：项目以Java后端求职为主，还需要可替换的AI处理能力。
- **最初方案**：整体计划选择Java管理业务、Python负责AI。
- **遇到的问题/权衡**：两套依赖、两套测试、跨网络失败；这个业务并非只能双语言实现。
- **当前方案**：一个Java业务应用加一个Python Mock HTTP服务，Python不写业务数据库。
- **为什么这样选择**：Java集中保护状态和记录，Python作为独立草稿助手便于以后接AI生态；已用真实双服务冒烟验证交接。
- **未来什么情况下需要升级**：真实模型接入或独立扩容有测量依据时调整接口与部署，不因为“微服务”名词继续拆业务。

## ADR-002 当前同步HTTP

- **问题**：先验证一条能运行的Java→Python→Java链路。
- **最初方案**：长期计划考虑异步任务，阶段2要求先完成直接调用。
- **遇到的问题/权衡**：同步会占用Java请求线程等待；异步需要任务状态、查询和失败恢复。
- **当前方案**：RestClient复用JDK HTTP/1.1，同步JSON，连接2秒/读取3秒，无自动重试。
- **为什么这样选择**：复用已有Spring Web，调用从上到下可读；超时和坏响应已有测试，网络调用不必再引入响应式框架。
- **未来什么情况下需要升级**：真实模型耗时超过请求预算、出现排队/取消/恢复需求时，设计持久任务和有界执行，不只增加线程数。

## ADR-003 暂时不使用MQ

- **问题**：生成是否需要消息队列中转。
- **最初方案**：长期路线以MySQL任务表考虑可靠异步，不预设必须上MQ。
- **遇到的问题/权衡**：MQ增加部署、消息确认、重投、幂等与业务写入一致性问题；当前没有异步消费者需求。
- **当前方案**：直接HTTP，无MQ、无任务表、无后台自动重试。
- **为什么这样选择**：先完成保存与人工确认闭环，减少排错组件；代价是不能在应用重启后自动恢复进行中的生成。
- **未来什么情况下需要升级**：需要削峰、多个消费者或跨业务事件分发时比较任务表与MQ；若选MQ，明确事务消息/outbox等一致性方案并做故障测试。

## ADR-004 Python调用期间不保持长数据库事务

- **问题**：慢网络调用可能长期占用数据库连接或锁。
- **最初方案**：容易想到把“读取→调用→保存”全圈在一个事务中，但本项目没有采用。
- **遇到的问题/权衡**：事务外调用会留出并发修改窗口；长事务也不能回滚Python已经产生的外部效果。
- **当前方案**：先读及检查，事务外生成，TransactionTemplate短事务条件更新并读回。
- **为什么这样选择**：节约连接占用，用版本条件挡住过期结果；代码明确可见事务边界，冲突与失败路径已验证。
- **未来什么情况下需要升级**：增加多表一致性或可靠任务时重划事务边界，但外部模型调用仍不应默认放进长事务。

## ADR-005 乐观锁保护人工内容

- **问题**：两个请求读取旧内容后可能互相覆盖。
- **最初方案**：仅在Java中先比较版本不够；本地锁也不能协调多个JVM。
- **遇到的问题/权衡**：检查与更新之间有竞态；冲突需要用户重新查询和决定。
- **当前方案**：UPDATE同时检查id/version/status，版本加1，影响0行返回409。
- **为什么这样选择**：保护条件在数据库执行处原子生效，无额外中间件；两个真实并发PATCH已验证一成一败。
- **未来什么情况下需要升级**：热点记录冲突率很高时先测量，再比较串行处理、悲观锁或业务合并，不能自动覆盖冲突。

## ADR-006 AI失败允许人工接管

- **问题**：助手故障不能让商家已经录入的问题无处处理。
- **最初方案**：整体计划要求“没有模型时人工业务仍能保存”。
- **遇到的问题/权衡**：必须区分原草稿和最终回复，不能把故障伪装为生成成功。
- **当前方案**：先保存咨询，Python失败返回错误且不改记录；PENDING允许人工SAVE/CONFIRM。
- **为什么这样选择**：Java仍管理正式台账，助手是辅助能力；真实停止Python后人工确认测试通过。MySQL本身不可用时不承诺人工持久化可用。
- **未来什么情况下需要升级**：商家试用需要协作追踪时增加授权范围内的操作者、审核历史和通知，而不是自动对客发送。

## ADR-007 MySQL持久化

- **问题**：原预览响应随请求结束，不提供跨重启历史与确认记录。
- **最初方案**：阶段2无数据库先验证协议；长期计划预留MySQL。
- **遇到的问题/权衡**：增加连接配置、表约束与数据库故障；内存替身无法证明真正保存。
- **当前方案**：使用现有localhost:3306的MySQL/InnoDB，一张consultation表。
- **为什么这样选择**：事务、条件UPDATE和索引适合当前台账；真实建表、落库、重复初始化及应用重启读回均通过。
- **未来什么情况下需要升级**：数据量和查询模式变化后先EXPLAIN与压测，再调整索引或分页；不预先分库分表。

## ADR-008 MyBatis和显式初始化SQL

- **问题**：新手需要看懂Java如何执行SQL，同时避免建表流程复杂化。
- **最初方案**：整体计划含MyBatis和Flyway。
- **遇到的问题/权衡**：自动ORM可能隐藏SQL；单表阶段引入迁移管理增加学习面，但手动脚本不适合长期连续升级。
- **当前方案**：MyBatis4.0.0注解SQL、Boot管理JDBC驱动；项目Java脚本执行可审阅CREATE IF NOT EXISTS，无Flyway。
- **为什么这样选择**：参数、索引、事务效果可直接对照SQL；不移动MySQL物理文件，重跑脚本不清除记录。
- **未来什么情况下需要升级**：首次出现跨环境的连续表结构演进时引入版本化迁移；已存在表不会因IF NOT EXISTS自动更新。

## ADR-009 单表、原稿与人工稿分开

- **问题**：既要保留助手输出，又要保存商家最终决定。
- **最初方案**：长期计划有独立草稿、证据、工单等多表。
- **遇到的问题/权衡**：当前只有一份原草稿和当前人工稿，多表会扩大范围；JSON不适合所有内部字段的频繁检索。
- **当前方案**：draft_result保存完整JSON快照，final_answer保存当前人工文本；确认后只读。
- **为什么这样选择**：单表完成最小追溯且人工编辑不覆盖原稿，测试逐步对比验证。
- **未来什么情况下需要升级**：需要多次生成、人工修改历史、证据版本或审计时再拆表并定义关系。
