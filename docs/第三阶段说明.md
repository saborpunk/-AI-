# 第三阶段：咨询持久化闭环

## 最小数据模型（实现前确定）

只有一张业务表 consultation，建表原文在 scripts/sql/001_create_consultation.sql。没有客户、账号、角色、历史版本或独立草稿表，无外键关系。一条咨询对应至多一份生成成功的 Python 草稿，以及一份当前人工回复；暂不允许重新生成覆盖原草稿。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | CHAR(36)，主键 | UUID 咨询编号，不依赖数据库自增 |
| question | VARCHAR(2000)，非空 | 原始问题，保留提交文字 |
| batch_code | VARCHAR(40)，可空 | 可选模拟批次号，不代表已核实批次 |
| status | VARCHAR(20)，非空 | PENDING / DRAFT_READY / CONFIRMED |
| draft_result | JSON，可空 | Python 完整结果快照，保留原草稿、requestId、缺失项、mock 与人工审核标识 |
| final_answer | VARCHAR(4000)，可空 | 人工编辑内容，与原始草稿分开 |
| version | BIGINT，初始0 | 每次有效修改加1，防止并发覆盖 |
| created_at / updated_at | DATETIME(6) | UTC 创建/更新时间，接口明确返回 UTC 偏移 |
| confirmed_at | DATETIME(6)，可空 | 确认时间，仅已确认时设置 |

索引：(created_at DESC, id DESC)，支持固定顺序的历史查询。状态、版本和确认必填项有数据库 CHECK 约束，应用还进行参数验证。用 JSON 保存一个小而完整的结果快照，避免提前拆出多张表；代价是当前不支持按草稿内部字段检索或多次生成历史。

## 接口与状态

| 接口 | 用途 | 成功 |
| --- | --- | --- |
| POST /api/v1/consultations | 保存 question、可选 batchCode | 201，返回 PENDING / version=0 |
| GET /api/v1/consultations/{id} | 查询一条记录 | 200；不存在404 |
| GET /api/v1/consultations?page=1&size=20 | 历史分页 | 200，items/page/size/hasMore |
| POST /api/v1/consultations/{id}/draft | 根据已保存问题生成并落库，请求含 version | 200，DRAFT_READY / version+1 |
| PATCH /api/v1/consultations/{id}/review | 提交 version、finalAnswer、action=SAVE 或 CONFIRM | 200，保存编辑或确认 |

PENDING 可以生成一次草稿，或者由人工接管保存/确认；DRAFT_READY 可以继续编辑或确认；CONFIRMED 只读。所有修改都检查 version，旧版本或非法状态返回409。用户必须提交实际确认的文字，不隐式把未检查的模拟草稿视为最终回复。

没有自动重试或持久队列。并发生成可能计算多次，但只有与当前 version 和 PENDING 状态匹配的一次结果能入库，其余409；不声称模型只调用一次。请求中断时查询已知咨询ID和版本，不能盲目认为失败就没有写入。重复创建咨询会产生新记录，本阶段不提供创建幂等键。

历史分页默认20条，最大100条，页码1–1000。使用 OFFSET 便于入门，规模较大时再测量并考虑游标分页；不声称已完成大数据性能优化。

## 一次请求如何落库

Controller 反序列化 JSON 并校验 → Service 判断业务状态 → TransactionTemplate 开始短事务 → MyBatis Mapper 通过绑定参数执行 SQL → MySQL 更新行 → 在同一事务读回结果 → 提交 → Controller 返回 JSON。

生成草稿时不同：先读已保存问题、检查版本 → **事务外**调用既有 PythonDraftClient → 验证 Python 响应 → 短事务执行带版本条件的 UPDATE 并读回 → 返回。如果 Python 出错，数据库中的原问题不变；如果调用期间人工已修改，旧结果不能覆盖新内容。

## 核心技术与为什么选择

1. **MySQL / JDBC**：MySQL 是能跨应用重启保留记录的台账；JDBC 驱动是 Java 与台账的通信接口。只连现有 localhost:3306，密码放项目忽略文件。
2. **MyBatis 4.0.0**：SQL 就写在 Mapper 上，绑定参数而非拼接用户输入，便于理解注入防护和以后分析索引。
3. **TransactionTemplate**：明确标出“更新和读回”共同成功的范围；失败回滚。没有把耗时 HTTP 调用圈进事务，减少连接与锁占用。
4. **乐观锁 version**：更新单据带上看过的版本，数据库只在版本仍相同时更新；比本机锁更适合防止不同请求的覆盖。
5. **原稿与人工稿分开**：Python 草稿 JSON 留作对照，人工修改只写 final_answer。它是简单的结果追溯，不是完整审计系统。

新增依赖：MyBatis Spring Boot Starter 4.0.0（包含 JDBC 自动配置和连接池）及 MySQL Connector/J（版本由 Spring Boot 管理）。仅一个小表，当前先执行可审阅的建表 SQL，不增加 Flyway；以后出现版本化数据库迁移需求，再单独引入。连接池最大5、最小空闲0、获取连接超时3秒；延迟连接允许数据库不可用时原有无数据库草稿预览继续运行。

## 文件职责

- consultation/Consultation.java：数据库行、API 视图、编辑动作和分页对象。
- ConsultationMapper.java：插入、查询、带版本更新的显式 SQL。
- ConsultationService.java：状态规则、事务边界、Python 生成和 JSON 快照转换。
- ConsultationController.java：5类 HTTP 操作的入口。
- ConsultationException.java：404/409 业务错误。
- ApiExceptionHandler.java：新增路径/分页校验、数据库错误处理。
- application.yml / pom.xml：连接池、MyBatis 配置与依赖。
- scripts/sql/001_create_consultation.sql：只初始化项目库表，不清空数据。
- scripts/DatabaseSetup.java：用本地配置连接现有服务，检查连接或执行 SQL；不操作物理文件。
- config/db.example.properties：可提交的配置模板；db.local.properties 被忽略，不提交。
- config/maven-mirror.xml：Central不可用时使用的项目内可选公开镜像配置。
- ConsultationServiceTest.java：不依赖实际数据库的业务规则测试。
- DatabaseUnavailableApiTest.java：在测试中让 DataSource 抛连接异常，验证 API 的503；不停止真实MySQL。
- scripts/check-persistence.py：真实 API 验收和应用重启后的读回检查，测试记录明确标识为合成数据。
- HealthEndpointTest.java：健康检查测试关闭数据库探测，避免该基础测试依赖本机MySQL；实际启动仍检查数据库健康。
- .gitignore：排除本地数据库凭据；AGENTS.md / MVP-v0.1.md：记录已确认的阶段边界。
- README.md / 开发记录.md / 测试报告.md：启动说明、问题处理过程和实际验收证据。

## 当前范围和下一步

不实现登录、前端、权限、Redis、RAG、真实AI、消息队列或微服务。原有 POST /api/v1/germination-drafts 保持无数据库预览接口，新增接口显式负责持久化，不改变旧响应约定。

本阶段真实MySQL闭环、并发修改、Python故障接管、Java重启读回和原接口回归均已通过，详情见测试报告。下一阶段建议先让商家走查这条 API 闭环的操作流程，再决定是否增加最小工作台；本阶段不会提前实现。
